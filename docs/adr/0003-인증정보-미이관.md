# ADR 0003 — 인증정보를 이관하지 않는다: 파티션별 1회 로그인

- 상태: 채택
- 날짜: 2026-09-15
- 관련: `CLAUDE.md`(불변 조건 9, "인증·로그인·임포트" 절), `goals/GOAL-M4c.md`,
  `src/main/sessions/LoginBroker.ts`, `src/main/browser/ProfileImport.ts`,
  `src/main/browser/PasswordImport.ts`, `eslint-rules/no-credential-files.mjs`,
  `artifacts/m4c/REPORT.md`

## 맥락

사내 브라우저를 갈아타는 사용자의 첫 기대는 "쓰던 그대로" 다 — 북마크도, 방문 기록도,
**로그인 상태도**. 앞의 둘은 가져올 수 있다. 마지막 하나를 가져오려는 순간 이 제품은
인포스틸러와 같은 코드를 갖게 된다.

### 왜 세션 쿠키·토큰 이관은 불가능한가 (기술)

- **ABE(App-Bound Encryption, Chrome 127+)**: Chrome 은 쿠키 암호화 키를 DPAPI 위에
  한 겹 더, **Chrome 자신의 서명된 바이너리만** 풀 수 있게 묶었다(`app_bound_encrypted_key`,
  ChromeElevationService 경유). 같은 사용자 계정의 다른 프로세스가 복호화를 시도하면
  서비스가 호출자 경로를 검증하고 거부한다. Edge 도 같은 구조를 따른다.
- **DBSC(Device Bound Session Credentials, 2026-05 GA)**: 세션 자체가 TPM 에 묶인
  키로 주기적 재증명을 요구한다. 쿠키 파일을 통째로 복사해도 **다른 기기·다른 앱에서는
  세션이 서지 않는다**. 이관이라는 개념 자체가 무효가 된다.

### 왜 시도조차 하지 않는가 (운영)

복호화를 시도하는 코드는 성공 여부와 무관하게 **인포스틸러의 시그니처**다.
`Cookies` 파일 접근 + `os_crypt` 파싱 + DPAPI 호출 조합은 EDR 이 탐지하는 바로 그
패턴이고, 사내 보안 솔루션에 걸리면 제품 배포 자체가 막힌다. "우리는 선의다" 는
바이너리에 적히지 않는다.

### 참고한 사례

- **Vessel Browser(MIT)**: 세션을 파티션 단위로 영구화하고 이관은 하지 않는다 —
  본 프로젝트의 Named Session(`persist:helm:<name>`) 설계가 같은 노선이다.
- **sync-multi-chat 류 멀티 계정 도구**: 계정마다 파티션을 나누고 **각 파티션에서
  한 번씩 로그인**시키는 방식이 실사용에서 충분히 통한다는 선례. 로그인 상태는
  파티션이 유지하므로 "한 번" 이면 된다.

## 결정

### 1. 이관하지 않는다. 대신 "한 번 로그인" 을 덜 아프게 만든다

로그인 획득 경로 3종(`LoginBroker`, `login_start(url, method)`):

| method | 언제 | 무엇을 하나 |
|---|---|---|
| `inapp` (기본) | 대부분의 사이트 | 로그인 페이지를 Helm 탭에서 열고 사용자가 직접 로그인 |
| `oauth_modal` | 임베디드 웹뷰를 거부하는 IdP | 서비스와 **같은 partition** 을 쓰는 모달 창에서 표준 redirect OAuth |
| `external` | 위 둘 다 막힌 예외 | 실제 기본 브라우저에서 인증만 마치고, Helm 이 세션 성립을 **검증**. 실패 시 `inapp` 폴백 |

공통 규칙:

- 세 경로 모두 비밀번호·토큰을 읽지도 쓰지도 않는다. 결과는 partition 안의 쿠키로만
  남고, 우리가 기록하는 것은 세션 메타(`{loginMethod, loggedInAt, verifiedHost}`,
  safeStorage 암호화)뿐이다.
- `oauth_modal` 의 UA 는 Electron 기본 UA 에서 `Electron/x.y`·`Helm/x.y` **토큰만 뗀**
  표준 Chromium UA 다(`stripElectronToken`). 우리가 Chromium 인 것은 사실이고 거짓말을
  보태지 않는다. 다른 브라우저인 척하는 문자열은 봇 탐지 우회라 금지다(불변 조건 9).
- `external` 은 `policy.externalLoginHosts` 화이트리스트 밖이면 **브라우저를 열기 전에**
  거부한다. 검증에 실패하면 조용히 넘기지 않고 `inapp` 으로 되돌린다 — 외부 브라우저의
  쿠키는 그 브라우저 것이라 Helm 세션은 서지 않기 때문이다.
- 세션 만료는 에이전트 안(`Agent.loginGate`)과 밖(`sessions/SessionExpiry.ts`) 모두에서
  감지해 스레드를 `waiting_login` 으로 내리고 받은편지함 `login_required` 카드(경로 3종
  버튼)로 사람에게 넘긴다. 로그인 후 마지막 체크포인트에서 재개한다(M4a 연동).

### 2. 최초 임포트는 3단계 정책으로 나눈다

1. **가져온다** — 북마크·방문 기록·자동완성. 비암호화 편의 데이터. 허용 목록
   (`Bookmarks`·`History`·`Web Data`)만 열고, SQLite 는 사본을 떠서 읽는다.
2. **동의하면 가져온다** — 저장된 비밀번호. `policy.allowPasswordImport` 가 true 이고
   사용자가 마법사에서 명시 동의한 경우만. 정책이 끄면 항목이 비활성 안내로만 남는다
   (숨기지 않는다 — "왜 없지?" 를 만들지 않기 위해).
3. **가져오지 않는다** — 세션 쿠키·인증 토큰. 선택지가 아니라 **고정 안내**다.
   "각 사이트에서 한 번 로그인하면 이후 유지됩니다."

모든 임포트는 `{what, count, sourceProfile, ts}` 를 감사 로그에 남긴다.

### 3. 비밀번호는 **Chrome 내보내기 CSV 경로만** 구현한다 (DPAPI 아님)

`goals/GOAL-M4c.md` 는 "CSV 또는 같은 사용자 DPAPI 복호화" 를 허용하지만, 같은 파일의
FIXED DECISIONS 가 lint 예외를 `Login Data` 에 대해서만 연다. 복호화 관용구
(`DPAPI`·`CryptUnprotectData`·`os_crypt`)는 `no-credential-files` 규칙의 예외 밖에
그대로 남아 있으므로, **DPAPI 경로는 이 규칙 아래에서 작성할 수 없다.**

그래서 사용자가 Chrome 화면에서 직접 내보낸 CSV 를 받는다. 우회가 아니라 더 정직한
경로다 — 무엇을 넘기는지 사용자가 Chrome 의 UI 에서 보고 결정한다. 이 경로는
`Login Data` 를 아예 건드리지 않아 예외조차 쓰지 않는다.

구현 규칙:

- 평문은 디스크에 쓰지 않는다. 한 줄씩 읽어 한 건씩 Windows 자격증명 관리자
  (`advapi32.dll` `CredWrite`, PowerShell P/Invoke — 의존성 0)로 넘기고, 비밀번호는
  **stdin 으로만** 전달한다(argv 는 프로세스 목록에 보인다).
- 끝나면 원본 CSV 를 0 으로 덮고 지운다(shred). 다운로드 폴더에 평문 비밀번호 파일이
  남는 것이 이 기능의 가장 큰 위험이다.
- 정책 게이트는 UI 와 IPC **양쪽**에 있다. renderer 를 믿고 화면에서만 숨기면 IPC 를
  직접 불러 우회할 수 있다.
- 감사 로그에는 건수·호스트만 남는다. 값은 물론 사용자 이름도 싣지 않는다.

### 4. lint 가 이 결정을 지킨다

`eslint-rules/no-credential-files.mjs`:

- `Cookies`(경로 형태)·`Local State`·`Affiliation Database`·복호화 관용구는 소스 전체에서
  금지. 미끼 파일 이름은 코드가 아니라 `fixtures/profiles/skip-names.json` 데이터로만
  존재한다.
- `Login Data` 만 좁은 예외: 그 파일에 `// policy:password-import` 주석과 감사 로그
  호출이 **둘 다** 있어야 통과한다. 주석은 선언이고 감사 호출은 기록의 보증이다.
- 나중에 DPAPI 경로를 켜려면 이 규칙의 복호화 관용구 차단을 **의식적으로** 푸는 별도
  결정(새 ADR)이 필요하다.

## 결과

- 사용자는 사이트마다 한 번 로그인하고, Named Session 파티션이 그것을 유지한다.
  임베디드를 거부하는 IdP 도 `oauth_modal` 로 들어온다. 검증: `npm run test:login`.
- 소스 어디에도 쿠키·토큰 복호화 코드가 없고, fixture 프로필의 자격증명 파일 접근이
  0건임을 파일 접근 로그로 확인한다. 검증: `npm run test:import`, `npm run lint`.
- 트레이드오프: DPAPI 직접 복호화보다 사용자 손이 한 번 더 간다(Chrome 에서 내보내기).
  받아들인다 — 그 손 한 번이 "사용자가 무엇을 넘기는지 아는 상태" 를 만든다.
- `externalLoginHosts` 의 운영 목록은 M6 `config/pilot.json` 에서 사람이 다시 정한다.
  지금 값은 검증용 모의 IdP 2종뿐이다.
