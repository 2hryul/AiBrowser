# ADR 0002 — 승인 3단계와 되돌리기의 경계

- 상태: 채택
- 날짜: 2026-09-10
- 관련: `CLAUDE.md`(불변 조건 4·5), `goals/GOAL-M3.md`, `src/main/control/Policy.ts`,
  `src/main/persistence/UndoManager.ts`, `artifacts/m3/REPORT.md`

## 맥락

"AI 가 하는 일이 사용자의 통제 아래 있다" 를 코드로 옮기려면 두 가지를 선으로 그어야 한다.

1. **무엇을 물어볼 것인가** — 전부 물으면 아무도 쓰지 않고, 안 물으면 통제가 아니다.
2. **무엇을 되돌릴 수 있다고 말할 것인가** — 되돌릴 수 없는 것을 되돌릴 수 있다고 표시하는 것이
   가장 나쁘다. 사용자는 되돌렸다고 믿고 넘어간다.

## 결정

### 1. 승인 대상은 "행위" 로 분류한다

도구 이름만으로 판단하지 않는다. `classifyAction()` 이 (도구, 인자, 대상 문구)를 보고
`write_click` / `form_submit` / `download` / `upload` / `javascript` / `site_first_visit` / `tool`
중 하나로 정하고, 앞의 다섯은 **항상** 승인 대상이다. 같은 `computer` 도구라도 "상신" 버튼을
누르는 것과 목록을 스크롤하는 것은 다른 행위다.

판정 순서는 하나로 고정한다: **도구 거부 → 사이트 거부 → 기존 승인 → 물어보기**.
자동 승인 플래그는 만들지 않는다. "묻지 않아도 되는 상태" 는 사람이 남긴 grant 뿐이고,
그 grant 에는 범위와 시각이 함께 기록된다.

### 2. 쓰기 키워드는 **대상 요소의 문구**로만 판정한다

`computer` 의 `type` 은 `args.text` 가 **입력할 내용**이므로 판정 근거에서 제외한다.
본문에 "청구액" 이라고 적었다는 이유로 쓰기 클릭 승인을 요구하면, 사람은 승인 창을 읽지 않고
누르는 습관을 들인다 — 승인 게이트가 있으나 없으나 같아진다.

대상 문구는 `read_page`/`find` 가 만든 ref 표의 접근성 이름에서 가져온다. 이 경로가 조용히
빈 문자열을 돌려주면 승인이 통째로 새므로, ref 표 조회는 **정적 import** 로만 한다
(번들 후 동작하지 않는 지연 `require` 로 실제 사고가 있었다 — `artifacts/m3/REPORT.md`).

### 3. 사이트 접근 승인은 그 실행 동안 유지된다

`site_first_visit` 을 사람이 허용하면 범위와 무관하게 그 호스트는 이번 실행에서
"방문 허가" 상태가 된다(`markVisited`). `once` 를 골랐다고 페이지마다 다시 묻지 않는다.

근거: 한 작업은 보통 같은 사이트의 여러 페이지를 지난다. 매 이동마다 묻는 설계는
승인 피로를 만들고, 피로해진 사람은 읽지 않고 누른다. 대신 **쓰기 행위는 이 완화와 무관하게
매번 판정**한다 — 사이트에 들어가도 되는 것과 그 사이트에서 무엇을 눌러도 되는 것은 다르다.

따라서 사이트 승인의 세 범위 차이는 "기록이 남는 범위" 다.
`once` 는 메모리에만 남고(재시작하면 사라짐), `thread` 는 그 실행 단위에,
`domain` 은 `policy.json` 에 남아 설정 화면에서 회수할 수 있다.

### 4. `irreversible` 과 `inverse` 는 상태를 바꾸는 도구에만 강제한다

lint 규칙 `require-tool-inverse` 는 `sideEffect: 'read'` 인 도구를 건너뛴다.

읽기 도구는 되돌릴 대상이 없어 `inverse` 를 만들 수 없고, 그렇다고 `irreversible: true` 로 두면
Policy 가 페이지를 읽을 때마다 승인을 요구한다. 규칙의 의도는 "모르는 채 못 되돌리는 일을
막는 것" 이므로, 읽기에까지 적용하면 의도와 어긋난다.

같은 이유로 `computer` 의 `screenshot`/`zoom`/`hover` 는 선언된 `sideEffect`('input')와 달리
판정 시 읽기로 취급한다(`effectiveSideEffect`). 한 도구가 조작과 관찰을 함께 담고 있어서다.

### 5. 제출 후에는 봉인한다

`write_click`/`form_submit` 승인이 나면 그 시점까지의 입력 항목(`form_input`·`computer type`)은
`sealed` 가 된다. 서버에 반영된 값을 화면에서만 되돌리면 "되돌렸다" 는 거짓말이 된다.
봉인된 항목은 버튼을 비활성으로 두는 대신 **사유를 함께 보여준다** — 왜 안 되는지 알아야
사람이 다음 수(문서 회수 요청 등)를 정할 수 있다.

`undo` 자체는 `irreversible: true` 다. 되돌리기의 되돌리기(재실행)는 만들지 않았다.
같은 조작을 다시 하는 것이 곧 재실행이고, 그때는 다시 승인을 받아야 한다.

## 남는 한계

- **금액과 사번을 숫자 모양으로 구분할 수 없다.** 사번 패턴은 "독립된 7자리 숫자" 인데
  `1200000` 같은 금액이 그대로 걸린다. 마스킹은 안전한 쪽으로 실패하지만(가려 버린다),
  금액을 다뤄야 하는 화면에서는 오탐이 일을 막는다. 모의 포털은 실제 결재 화면처럼
  천 단위 쉼표를 넣어 이 문제를 피했고, 실제 포털에서는 호출부가 `kinds` 로 적용 범위를
  좁히거나 필드 문맥(라벨)을 함께 보는 규칙이 필요하다. M4 이후 과제.
- **grant 는 호스트 단위다.** 경로별(`/hr/*` 만 허용) 범위는 없다.
- **`thread` 범위는 실행 단위(runId)** 다. 진짜 스레드는 M4 에서 도입되며, 그때 승격한다.
