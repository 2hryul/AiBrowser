# 모델 평가 — 로컬 LLM 능력 실측

`npm run probe:llm [모델]` 의 결과를 옮겨 적는다. 시나리오별 성공률·평균 스텝·LLM 호출 수 표는
M4b 에서 채운다(GOAL-M4 M4b 성공 조건 7). 지금 이 문서에 있는 것은 **M4b 를 시작할 수 있는지**를
판단하기 위한 사전 실측이다.

```powershell
npm run probe:llm                       # 기본 모델(qwen2.5:7b-instruct) 능력 4종 + 루프 1회
npm run probe:llm qwen2.5:7b-instruct --loop 3   # 루프만 3회
```

Electron 을 띄우지 않고 Ollama 엔드포인트만 두드린다. 도구 결과는 포털 A 모양으로 흉내낸다 —
여기서 보는 것은 브라우저가 아니라 **모델의 판단과 루프 행동**이다.

`navigate → get_page_text → record_rows` 를 10페이지 동안 순서대로 지키고, 마지막에

temperature 0 이라 3회가 거의 같았다.

### 이 실측에서 나온 두 가지 (M4b 설계에 반영해야 함)

**1. "읽고 나서 기록하라" 를 명시하지 않으면 데이터를 지어낸다.**

1차 시도의 프롬프트에는 순서 규칙이 없었고 `record_rows` 가 `count` 만 받았다. 결과:

```
 1. navigate {"url":"app://portal-a/list?page=1"}
 2. record_rows {"count":10,"page":1}      ← get_page_text 를 아예 부르지 않았다
 ...
21. done {"total":100}                     ← 실제 200
```

페이지네이션·루프 종료는 완벽했지만 **한 페이지도 읽지 않고** 행 수를 10으로 지어냈다.
고친 방법 두 가지 — 둘 다 필요했다:

- 시스템 프롬프트에 `navigate → get_page_text → record_rows` 순서와 "짐작하지 않는다" 를 명시
- `record_rows` 가 `firstId`·`lastId` 를 요구 — **페이지를 읽지 않으면 채울 수 없는 인자**

두 번째가 더 중요하다. 프롬프트는 무시될 수 있지만, 검증 가능한 인자는 거짓이 드러난다.
M4b 의 도구 스키마는 이 원칙을 따라야 한다.

**2. 문맥이 8k 상한에 닿는다.**

10페이지 시나리오 하나에서 최대 프롬프트가 **8,048 토큰**이었다(GOAL-M4 의 `LLMClient` 상한 8k).
행을 대화에 다시 적지 않게 해도 도구 결과(페이지 본문)만으로 여기까지 온다. 추출한 뒤 오래된
페이지 본문을 버리는 문맥 정리는 최적화가 아니라 **필수**다.

### 판정

- **능력으로는 대체 가능하다.** 도구 호출·다단계·구조화 출력·주입 저항이 모두 동작하고,
  400행 순회를 3/3 완주했다.
- **단, M4b 성공 조건의 숫자가 뜻하는 바가 달라진다.** "3회 중 2회 성공" 과
  "MacroCache 로 LLM 호출 50% 감소" 는 27B/30B 급을 전제로 쓰인 값이다. 7.6B 로 측정한
  성공률은 같은 이름의 다른 숫자다 — 그래서 이 표에는 **모델 이름을 반드시 함께 적는다.**
- 모델 교체는 사람 결정이다(GOAL-M4 STOP CONDITIONS).

### 실패 패턴 — 한 줄로

**이 모델은 한 화면을 읽고 뽑는 것은 하지만, 그 일을 열 번 이어서 하지 못한다.**

- 1페이지를 읽고 20행을 정확히 뽑은 뒤, 2페이지로 넘어가지 않는다.
  루프가 "다음 화면으로 가라" 를 매 단계 알려 줘도 같은 화면을 다시 읽거나 끝났다고 말한다.
- 시나리오 B(단일 XHR)에서는 `read_network_requests` 를 12번 부르면서도 행을 한 건도
  기록하지 못했다. 읽기 우선순위는 지켰다 — **읽은 것을 결과로 옮기는 자리**에서 멈춘다.
- 2026-09-12 앞 항목의 프로브 루프가 3/3 이었던 것과 모순되지 않는다. 그때 도구는
  행이 아니라 **건수**(`record_rows{page,count,firstId,lastId}`)만 받았다. 실제 데이터를
  요구하자 같은 모델이 같은 루프를 완주하지 못한다.

### 흔들림(비결정성)

가벼운 요약은 단독 실행에서 통과했지만 시나리오 B 뒤에 이어 돌렸을 때는 실패했다.
같은 프롬프트·같은 모델에서 결과가 갈린다는 뜻이고, "3회 중 2회" 판정 기준이 있는 이유다.
한 번 통과한 것을 통과로 적지 않는다.

### 판정 — GOAL-M4 STOP CONDITIONS 적용

> M4b에서 5회 중 3회 미만 성공이 프롬프트·MacroCache 개선 3라운드 후에도 지속 → STOP,
> eval.md에 실패 패턴 기록(**모델 교체는 사람 결정**)

다섯 라운드를 돌았고 0/3 이 유지된다. 여기서 멈추고 사람의 결정을 기다린다.
**기준을 낮추지 않는다** — "3회 중 2회 · 200행 · 중복 0" 은 그대로 둔다.

사람이 고를 수 있는 것:

1. **더 큰 모델로 다시 잰다.** GOAL 원안의 `qwen3.6:27b` 급. 이 PC 의 VRAM 을 넘으므로
   CPU 오프로드(느림)를 감수하거나 다른 장비가 필요하다. 계측은 그대로 돌아간다 —
   `config/llm.json` 의 `model` 만 바꾸면 된다.
2. **7B 로 가되 작업 범위를 좁힌다.** 한 화면 수집·요약·질의는 지금도 된다.
   여러 화면 순회는 M5 의 워크플로우(사람이 승격한 결정적 절차)에 맡긴다.
   이 경우 M4b 성공 조건 2·3 을 사람이 다시 쓴다.
3. **Anthropic 어댑터로 상한을 확인한다.** `config/llm.json` 의 `provider` 를 바꾸고
   `apiKeyEnv` 를 지정하면 같은 시나리오가 그대로 돈다. 사내 배포용이 아니라
   "에이전트 설계가 문제인가, 모델이 문제인가" 를 가르는 데 쓴다.

어느 쪽이든 **코드를 고치는 일이 아니다.** 계측·가드·추출은 그대로 쓰인다.


## 2026-09-13 — 앞의 결론을 바로잡는다: 대부분 우리 쪽 결함이었다

어제(2026-09-12) 이 문서에 적은 실패 패턴은 **틀렸다.**

> ~~이 모델은 한 화면을 읽고 뽑는 것은 하지만, 그 일을 열 번 이어서 하지 못한다.~~

모델을 바꿀지 말지를 이 문장 하나로 정하게 되어 있었으므로, 근거를 다시 봤다.
**감사 로그와 스레드 대화를 실제로 읽었고**, 거기서 나온 것은 모델의 한계가 아니라
우리 코드의 결함 다섯 개였다. 숫자만 보고 모델 탓을 한 것이다.

### 무엇을 놓쳤나 — 기록을 읽고 찾은 다섯

| # | 실제로 벌어진 일 | 어디가 잘못이었나 |
|---|---|---|
| 1 | 탭이 `app://portal-a/login?next=…` 에 있었다. **1페이지에 닿은 적이 없다** | CLAUDE.md 가 요구한 "로그인 리다이렉트 감지 → waiting_login" 이 에이전트에 없었다 |
| 2 | `read_page → read_page` 되풀이를 캐시가 **매크로로 학습**해 증폭했다 | 자기 자신으로 가는 전이를 배우면 안 된다. 되풀이는 규칙이 아니라 막힌 신호다 |
| 3 | 같은 질문을 세 번 하고도 계속 돌았다 | 반복 감지가 "계속" 답을 받으면 무한히 다시 물었다 |
| 4 | 2회차가 자기 탭(4)을 열어 두고 **1회차의 탭(3)** 을 만졌다 | 캐시가 `tabId` 를 인자째 저장했다. 탭 번호는 실행마다 바뀌는 손잡이다 |
| 5 | 모델이 `navigate{url:"?page=2"}` 로 **페이지를 넘기려 했고 도구가 거절했다** | 상대 주소를 풀지 않았다. 게다가 그 형식은 우리가 도구 설명에 적어 준 예시였다 |

5번이 특히 뼈아프다. **모델은 우리가 시킨 대로 했고, 우리 도구가 그것을 거절했다.**
브라우저가 링크를 따라갈 때 늘 하는 일(상대 주소 풀기)을 도구가 안 하고 있었다.

### 고친 뒤의 측정 — 이제야 모델을 본 것이다

다섯 개를 고치고 같은 시나리오를 다시 돌렸다(러너가 사람 자리에서 먼저 로그인).

| 회차 | 판정 | 수집 | 중복 | 모델 호출 | 캐시 | 멈춘 이유 |
|---|---|---|---|---|---|---|
| 1 | FAIL | 1행 | 3 | 14 | 0 | incomplete |
| 2 | FAIL | 21행 | 4 | 14 | 0 | incomplete |
| 3 | FAIL | 20행 | 0 | 17 | 1 | incomplete |

**남은 실패 패턴(수정본)**: 로그인·캐시·주소 문제를 모두 걷어낸 뒤에도,
`qwen2.5:7b-instruct` 는 **1페이지를 읽고 20행을 정확히 뽑은 다음 다음 장으로 넘어가지

이것이 어제 적은 문장과 표면적으로는 같아 보이지만, **근거가 다르다.**
어제는 로그인 화면에서 헤매는 것을 보고 그렇게 적었고, 오늘은 정상 동작하는 루프에서
같은 자리에 멈추는 것을 보고 적는다.

### 그래서 "설계 문제인가 모델 문제인가" 는 아직 열려 있다

어제는 "설계는 맞고 모델이 한계" 라고 적었다. 오늘 드러난 것은 **설계에도 결함이 다섯 개
있었다**는 것이다. 지금은 그 다섯이 없고 루프는 건강하다 — 로그인을 감지하고, 캐시가
헤매지 않고, 상대 주소가 통한다. **이 상태에서 더 큰 모델을 붙이는 것이 비로소 깨끗한
실험이 된다.**

Anthropic 어댑터 비교 실행은 `ANTHROPIC_API_KEY` 만 있으면 바로 돌아간다
(어댑터 배선 테스트 11건 통과, 환경변수로 공급자 교체 가능).

### 배운 것 — 숫자만 보고 원인을 적지 않는다

`artifacts/m4b/agent-summary.json` 의 `rows: 1` 만 보고 "모델이 못 한다" 고 적었다.
같은 실행의 **스레드 대화 두 화면**을 읽었으면 첫날에 알 수 있었다.
실패한 실행은 숫자가 아니라 기록으로 읽어야 한다.

그래서 이번에 감사 로그도 함께 고쳤다 — **거절된 도구 호출이 로그에 아예 없었다.**
이제 남고, 어긋난 인자 이름을 말해 준다.
