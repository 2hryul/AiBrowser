- **결정 사항**
  - **`handoff` 는 성공이 아니다.** "여기까지는 했고 나머지는 다른 수단이 맞다" 는 보고다.
    스레드는 `done`/`needs_workflow` 로 닫는다 — 에이전트는 자기 몫을 끝냈고, 실패로 적으면
    "고장" 으로 읽힌다
  - **경계로 인정하는 조건 넷을 모두 요구한다.** 목표 미달 · 한 화면 5행 이상 수확 ·
    목표가 수확의 2배 이상 · **서로 다른 화면 둘 이상**. 마지막 조건이 없으면 한 자리에서
    한 화면 몫도 못 한 실행이 경계로 위장된다(시나리오 B 가 실제로 그랬다)
  - **수확량은 최대치로 본다.** 마지막 수확으로 보면 재방문(전부 중복 → 0행) 때문에
    네 화면을 돈 실행이 "한 화면도 못 했다" 로 판정된다. 질문이 "할 수 있는가" 이므로 답은 최대치다
  - **조건 3(시나리오 B)은 경계로 바꿔 쓰지 않았다.** B 가 못 하는 것은 순회가 아니라
    한 화면이다. 한 화면을 못 한 것을 넘김으로 부르면 실패를 위장하는 것이다. 범위만 좁히고
    (전량 137건 → 첫 응답 50건) 판정은 **FAIL 그대로** 적었다
  - **MacroCache 의 "LLM 호출 50% 감소" 는 뺐다.** 실행이 예산 벽의 서로 다른 지점에서
    멈추므로 회차 간 호출 수가 비교 가능한 양이 아니다. 이것은 **기준 완화**이므로 목표 파일에
    이유와 함께 명시하고 숫자는 `eval.md` 에 그대로 남겼다
  - 승격 안내 문구를 "넘길 수 있습니다" → **"초안을 만들 수 있습니다"** 로 낮췄다.
    이 포털용 어댑터가 없으면 초안의 수집 단계가 비고 승격 화면이 "어댑터를 직접 적어야
    한다" 고 말한다. 과장하면 다음 사람이 속는다

- **실측으로 잡은 결함 다섯 (전부 우리 쪽)**
  1. **XHR 결과를 봉투째 잘랐다.** `JSON.stringify(result)` 가 주소·상태·바이트 수까지 담아
     6,000자 상한을 메타데이터가 먼저 먹고, `body` 는 이스케이프된 문자열로 들어가 중간에서
     끊겼다 → 응답 본문만 넘긴다
  2. **모델이 날짜를 고쳐 썼다.** 포털은 `2026-01-01` 을 보여 주는데
     `2026-01-01T00:00:00.000Z` 로 적었다. 세 회차 **정확히 20건씩**. 프롬프트에 "YYYY-MM-DD 로
     맞춘다" 가 이미 있었다 → 모델이 쓴 값을 **본문에 대조**해 되돌린다. 형식은 코드가 지킨다
  3. **상대 주소가 host 를 지웠다.** `navigate` 는 `finalUrl` 을 주는데 `urlOf` 는 `result.url`
     만 봤다. `?page=2` 로 넘기면 그 조각이 현재 주소가 되고, 매크로 키·사이트 메모·메모 제안이
     전부 그 host 를 쓴다 → `finalUrl` 우선, 인자는 절대 주소일 때만.
     9/13 의 상대 주소 수정이 열어 둔 구멍이었다
  4. **50건 화면을 조용히 9행으로 잘랐다.** 10KB JSON 이 상한에 걸렸다. 조용히 자르면
     "화면에 9건뿐" 과 "9건까지만 보여 줬다" 가 구별되지 않는다 → 4,000자씩 겹쳐 나눠 뽑는다.
     추출 호출은 매번 새 대화라 루프 예산과 무관하다
  5. **측정 도구가 실패한 실행의 숫자를 잃었다.** 판정 `expect` 가 깨지면 Playwright 가 워커를
     새로 띄우고, 빈 `summary` 가 앞 시나리오 기록을 덮었다. 두 번 겪었다 → 회차마다 저장하고
     파일과 합친다. 9/13 에 "실패한 실행은 숫자가 아니라 기록으로 읽어야 한다" 고 적어 놓고
     정작 실패하면 숫자를 잃는 구조였다
